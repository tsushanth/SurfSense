# SurfSense Chrome Extension 4.0.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax. **This is a spec-level plan:** it fixes interfaces, required behavior and the exact tests to write; the implementer writes the code (plain ES modules, no build step, no bundler, no npm dependencies) and the tests (`node --test`).

**Goal:** Ship an extension (manifest version 4.0.0) that registers reliably, survives Manifest V3 service-worker restarts, records time per site correctly, uses the device's local calendar date like the Android app, and talks to the live backend without recreating the bugs found in 3.0.

**Architecture:** All network access and identity live in one ES module (`lib/api.js`) owned by the background service worker; the popup never calls the network, it sends messages to the background. Time accounting (`lib/tracker.js`) persists its state in `chrome.storage.local` and is driven by `chrome.alarms` (a `setInterval` does not keep an MV3 worker alive). Per-day totals are cumulative and the sync REPLACES the server's summary for that day (idempotent, like Android), instead of adding to it. Pure logic is unit-tested with fake storage/fetch; one scenario test drives `background.js` against a fake `chrome` and a fake backend.

**Tech Stack:** Chrome Manifest V3, ES modules, `chrome.storage.local`, `chrome.alarms`, Node's built-in test runner (`node --test`, Node 20+), no dependencies.

**Spec:** `docs/superpowers/specs/2026-10-12-surfsense-revival-and-redesign-design.md`; backend contract: `backend/server.js` (live at https://usage-tracker-backend.fly.dev).

## Findings in extension 3.0 (all verified by reading the code)

1. Registration happens ONCE in `onInstalled` and only if no `extensionId` exists; the id is stored before the request, so a failed registration (offline) is never retried and the extension stays unauthenticated forever. There is no 401 handling: after the backend DB was wiped, every existing install holds a key the server does not know and every call fails permanently. (The backend never re-issues a key for an id it already knows: a re-register of a known id returns 200 WITHOUT `apiKey`.)
2. Dates use `new Date().toISOString()` (UTC). The Android app uses the device's LOCAL date, so in the evening (US time zones) the two clients look at different days and never see each other's data.
3. Usage is sent only on the first tab switch after UTC midnight and stamped with the NEW day's timestamp, so yesterday's time is filed under today, and today's data reaches linked devices only when the user presses refresh.
4. MV3 service worker state (`activeTabId`, `activeStartTime`, `lastUsedDate`) lives in memory and the 60 s `setInterval` does not keep the worker alive: when Chrome stops the worker (~30 s idle) the active session is forgotten and that time is never recorded.
5. `get-category-mapping` is called with every domain at once (the backend accepts at most 100) and the response is not checked, so more than 100 domains turns everything into "Uncategorized".
6. `popup.js` makes its own network calls with its own copy of the auth helper, UTC dates, and no error handling for a wrong linking code.
7. `chrome://`, `about:` and extension pages are recorded as "domains".

## Global Constraints

- `manifest.json`: `"manifest_version": 3`, `"version": "4.0.0"`, host permission only `https://usage-tracker-backend.fly.dev/*`, permissions exactly `tabs`, `storage`, `alarms` (no others), background `{"service_worker": "background.js", "type": "module"}`, CSP unchanged (`script-src 'self'; object-src 'self'`).
- Backend base URL `https://usage-tracker-backend.fly.dev` (no trailing slash in the constant). Client type exactly `CHROME_EXTENSION`.
- Category names, exact spelling: `Social Media`, `Entertainment`, `Work/Productivity`, `Shopping`, `Education`, `News`, `Finance`, `Health`, `Travel`, `Food`, `Other`. A domain the server does not map becomes `Other` (never `Uncategorized`).
- `/get-category-mapping` accepts at most 100 domains per request: send batches of at most 100.
- A day is the browser's LOCAL calendar date `yyyy-MM-dd`. Summaries are submitted with `timestamp` = that date string (the backend turns `yyyy-MM-dd` into UTC midnight of the same date) and read with `day` = that date.
- Only `http:` and `https:` pages with a hostname are tracked; the stored domain has a leading `www.` removed and is lowercased. Never record paths, queries or titles.
- No secrets, API keys or ids in console logs. No remote code, no `eval`, no inline scripts.
- Do not modify `chart.umd.js`. Existing UI markup/styling stays (`popup.html` may change the `<script>` tag to `type="module"`; new strings only if unavoidable).
- Work in the git worktree `~/Documents/GitHub/SurfSense-extension` (branch `extension-4`); never touch `~/Documents/GitHub/SurfSense` (it has unrelated uncommitted iOS and extension edits). Stage by explicit path only; commit messages end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- Run tests with `cd extension && node --test` (Node 20+, built-in runner only).

## Review Focus

1. **First run offline / backend asleep:** the identity (random UUID) exists and is stable, registration is retried on the next call, nothing throws into the user's face. Task 1.
2. **Backend forgot this install (401):** exactly one re-registration and one retry; a 200-without-key answer means the id is burned and a NEW id is generated. Concurrent calls must not burn ids. Task 1.
3. **Service worker killed mid-session:** the active session is persisted; after a restart the next tick still banks the elapsed time (capped, see Task 2). Task 2, 3.
4. **Midnight:** a session spanning local midnight is split between the two days; the previous day is flushed under its own date. Task 2, 3.
5. **Sleep/hibernate:** a laptop asleep for hours must not count as usage (gap cap). Task 2.
6. **More than 100 domains:** batched, nothing becomes "Uncategorized". Task 1.
7. **Wrong linking code:** the popup shows the server's message ("Invalid or expired code"), not a generic failure. Task 3.

### Task 1: API module (identity, registration, 401 recovery, batching)

**Files:** create `extension/lib/dates.js`, `extension/lib/api.js`, `extension/tests/dates.test.js`, `extension/tests/api.test.js`.

**Interfaces (Produces):**
- `lib/dates.js`: `localDate(ms: number): string` (local `yyyy-MM-dd`), `startOfNextLocalDay(ms: number): number` (epoch ms of the next local midnight, DST-safe), `chunk(items: any[], size: number): any[][]`.
- `lib/api.js`: `createApi({ storage, fetchImpl = fetch, base = BACKEND_BASE, newId = () => crypto.randomUUID(), clientName: () => string })` returning an object with: `ensureRegistered(): Promise<boolean>`, `categorize(domains: string[]): Promise<Record<string,string>>` (batches of 100, throws `ApiError` on a non-OK batch, missing keys filled with `Other`), `submitSummary(day: string, summary: Record<string,number>): Promise<void>`, `getSummaryHistory(userId: string, day: string): Promise<Array<{timestamp,userId,summary}>>`, `initiateLinking(): Promise<string>`, `completeLinking(code: string): Promise<{linkedWith?: string}>`, `unlinkDevice(otherClientId: string): Promise<void>`, `getLinkedClients(): Promise<Array<{clientId,clientName,clientType}>>`, `getIdentity(): Promise<{extensionId: string|null}>`. Also exports `class ApiError extends Error { status: number, serverMessage: string|null }`, and `BACKEND_BASE`, and `messageFor(error): string` (user-facing text: offline/network error "No connection. Check your internet and try again."; 401/403 "This device isn't recognized by the server. Open the extension again to reconnect."; 429 "Too many requests. Try again in a minute."; 5xx "The server is having trouble. Try again soon."; other 4xx with a server message: that message verbatim; otherwise "Something went wrong.").
- `storage` is an object `{ get(keys: string|string[]): Promise<object>, set(obj: object): Promise<void>, remove(keys: string|string[]): Promise<void> }` (a tiny wrapper over `chrome.storage.local`; tests use an in-memory fake). Keys used by the API module: `extensionId`, `apiKey`.

**Required behavior:**
- `ensureRegistered()`: returns true immediately (no network) when `apiKey` is stored. Otherwise creates/reads `extensionId` (random UUID via `newId`, persisted BEFORE the request so it is stable), POSTs `/register-client` `{clientId, clientType: "CHROME_EXTENSION", clientName}`; 201/200 with `apiKey` => store it, return true; 200 without `apiKey` (server already knows the id, key lost) => remove `extensionId`, create a NEW id and try once more; network error or non-2xx => return false and keep the id. All registration work is serialized with an in-memory promise chain/mutex so concurrent callers do not register twice.
- Every authenticated call first awaits `ensureRegistered()` (if it returns false the call throws an `ApiError` with status 0 and the offline message, without sending the request), sends `Authorization: Bearer <apiKey>`, and on HTTP 401 (never for `/register-client`) performs `recoverAuth()` ONCE: inside the mutex, if the stored key differs from the key the failed request used, just retry with the stored key (another caller already recovered); otherwise remove the stored key, re-register (same id first, new id on the burned-id path) and retry the request once. A second 401 is returned as an `ApiError`.
- Non-2xx responses throw `ApiError(status, serverMessage)` where `serverMessage` is the JSON `error` string if present; a thrown fetch error (network) is rethrown as `ApiError(0, null)`.
- `getLinkedClients` and others send the identity's own id (`extensionId`) where the backend requires `clientId`/`userId`; `unlinkDevice` sends `{clientIdA: ownId, clientIdB: other}`; `completeLinking` sends `{clientId: ownId, code}`.
- No retries other than the single 401 recovery (keep it simple; callers are alarm-driven).

**Tests (write first; `node --test`):**
- [ ] `dates.test.js`: `localDate` uses LOCAL fields (construct a Date with `new Date(2026, 9, 12, 23, 30)` and assert `2026-10-12` even though it is Oct 13 in UTC for a western zone: build the expected string from `getFullYear/getMonth/getDate`, not from a hard-coded zone); `startOfNextLocalDay` returns midnight (hours/min/sec/ms all 0) of the next date and is strictly greater than the input; works across a month end and across the DST day (assert via `new Date(x).getDate()` differences, not hard-coded offsets); `chunk` splits 250 into 100/100/50, handles empty and exact multiples.
- [ ] `api.test.js` (fake storage, fake fetch recording calls, scripted responses): first registration stores id+key and sends type `CHROME_EXTENSION`; the id is persisted before the request (assert storage has it when the fetch is invoked); offline first call => false, id kept, next call registers; 200-without-key => new id and second registration; two concurrent `ensureRegistered()` => ONE register request; an authenticated call with a stale key: 401 => one re-register with the SAME id => retried once with the new bearer => success; the retried call also 401 => `ApiError(401)` and no third request; 401 where another caller already refreshed the key (stored key differs from the key used) => no register request, retried with the stored key; 401 on `/register-client` is not retried; `categorize` with 250 domains => three requests of 100/100/50 and all domains present in the result, a domain missing from the server answer => `Other`, a 400 batch => throws `ApiError`; `getSummaryHistory`/`submitSummary` URLs and bodies exactly as the backend expects (`/get-summary-history?userId=...&day=...`, body `{userId, timestamp: day, categorySummary}`); `completeLinking` 400 with `{"success":false,"error":"Invalid or expired code"}` => `ApiError.serverMessage === "Invalid or expired code"` and `messageFor(error) === "Invalid or expired code"`; `messageFor` table (offline, 401, 403, 429, 503, plain 400 without message).

### Task 2: Time tracker (persisted sessions, local days, midnight split, flush)

**Files:** create `extension/lib/tracker.js`, `extension/lib/sync.js`, `extension/tests/tracker.test.js`, `extension/tests/sync.test.js`.

**Interfaces (Produces):**
- `lib/tracker.js`: `domainOf(url: string): string | null` (http/https only, hostname lowercased, leading `www.` removed, otherwise null); `createTracker({ storage, now = () => Date.now() })` returning `{ activate(tabId: number, url: string|null): Promise<void>, navigate(tabId: number, url: string|null): Promise<void>, pause(): Promise<void>, tick(): Promise<void>, snapshot(): Promise<{ days: Record<string, Record<string, number>>, dirty: Record<string, number> }>, markFlushed(day: string, rev: number): Promise<void>, getToday(): Promise<Record<string, number>> }`. Constants exported: `MAX_GAP_MS = 150000`.
- `lib/sync.js`: `flushDirty({ api, tracker }): Promise<{ flushed: string[], failed: string[] }>`.
- Storage keys used: `session` (`{tabId, domain, lastMs}` or null), `days` (day -> domain -> seconds), `dirty` (day -> revision number), `rev` (counter).

**Required behavior:**
- All tracker operations are serialized (internal promise chain) so alarm ticks and tab events never interleave.
- `activate(tabId, url)`: bank the running session (as `tick` would), then, if `domainOf(url)` is non-null, start a new session `{tabId, domain, lastMs: now()}`; if the url is not trackable, store `session = null`. `navigate(tabId, url)`: same as activate but only when `tabId` equals the active session's tab or there is no session (a background tab navigating is ignored). `pause()`: bank and set `session = null`.
- Banking (`tick`): elapsed = `now() - session.lastMs`; if elapsed <= 0 do nothing; count `min(elapsed, MAX_GAP_MS)` ms (the rest is assumed sleep/suspend and discarded); split the counted interval at local midnights (`startOfNextLocalDay`) so each day gets its own seconds; add whole seconds to `days[day][domain]` (keep a sub-second remainder in the session so repeated ticks lose nothing: store `carryMs` in the session); every day touched gets `rev += 1` and `dirty[day] = rev`; then `session.lastMs = now()`. Ticks do NOT close the session.
- `snapshot()` returns deep copies. `markFlushed(day, rev)` removes `dirty[day]` only if `dirty[day] === rev` (changes made during the flush keep the day dirty); then prunes `days` entries older than 3 local days that are not dirty.
- `getToday()` returns today's (local) domain -> seconds map after banking the active session (so the popup shows live numbers).
- `flushDirty`: take a snapshot after `tracker.tick()`; for each dirty day in ascending order with at least one domain: `categories = await api.categorize(domains)`, aggregate seconds by category (missing => `Other`), `await api.submitSummary(day, summary)` (REPLACES the server's value for that day), then `tracker.markFlushed(day, rev)`. A day with no domains is marked flushed without a request. If a day fails (any thrown error) record it in `failed` and continue with the next day; never throw.

**Tests (write first):**
